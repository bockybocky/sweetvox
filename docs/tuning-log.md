# 甜嗓 SweetVox — 調整過程全紀錄（含失敗）

> 2026-09-22 開工 ～ 2026-10-08。
> 這份文件刻意把**走錯的路跟走對的路寫一樣詳細**。
> 最後有用的東西只有兩樣，而花掉的時間有八成在另外五樣上面 —— 那八成才是這份紀錄的重點。

---

## 0. 起點

**想要的**：聽 YouTube Music 的時候，女聲甜、清楚、往前站，伴奏退後。

**訊號鏈**（2026-10-04 才正式確認，這個延誤本身就是一個教訓）：

```
Chrome / YouTube Music
  → Equalizer APO（所有處理都在這裡）
  → Audiolab M-DAC（USB）
  → Onkyo TX-NR838，PURE AUDIO 模式
  → Discovery MD-103 喇叭
  → 房間 ← 整整兩週沒有人量過這一段
```

開工時訂了一條規矩：**沒有數字不算過**。每一層都要量過才往下走。
這條規矩最後救了這個專案好幾次 —— 它否決掉的東西比它通過的多。

---

## 1. 第 1 層：mid/side 女聲前移（成功，而且一直在跑）

2026-09-22 完成。用 Equalizer APO 的 `Copy:` 指令把 L/R 拆成
MID（正中央）與 SIDE（兩側），各自上濾波器之後再無損還原。

```
拆：  R = 0.5*L + -0.5*R  ;  L = L + -1.0*R
還原：L = L + R           ;  R = L + -2.0*R
```

離線量測（3 kHz 正弦、輸入 RMS −21.07 dB）：

- 純正中（女聲）：−1.11 dB（理論 −1.10）
- 純側面（伴奏）：−8.53 dB（理論 ≈ −8.4）
- 判別點：如果 `Copy:` 被忽略，純側面只會 −3.5 dB。量到 −8.53 → 中側矩陣真的在跑。

第一版 Preamp 設 −2.0 dB 會削波（175,314 個樣本），改成 −3.5 dB。

**當下的結論**：女聲相對伴奏 **+7.42 dB**，門檻是 3 dB，大勝。

**兩週後發現這個數字誤導了我們。** 見下一節。

---

## 2. 失敗（一）：拿兩把不同的尺比較，結論整個反過來

2026-10-04，要決定「神經網路分離」值不值得做，拿它的 **+3.00 dB** 去跟第 1 層的 **+7.42 dB** 比，
下了結論：「神經網路比現役的 EQ 差 4.4 dB，不要做。」

**這個結論是錯的，而且錯得很徹底。**

那兩個數字量的根本不是同一件事：

| 量的是什麼 | 靜態 mid/side 的成績 |
|---|---|
| **中央 vs 兩側**的能量比（+7.42 的那把尺） | +4.02 dB |
| **人聲 vs 伴奏**的真實比例（神經網路用的那把尺） | **+0.07 dB** |

用同一把尺重量之後，神經網路其實**贏約 3 dB**，不是輸。

**根因**：原本的驗收門檻隱含一個假設 ——「正中央＝女聲」。
但商業流行樂的**大鼓、貝斯、小鼓全部都在正中央**。
mid/side 幾乎沒有把人聲從伴奏裡拉出來，它只是改變了中央與兩側的比例。

**教訓**：比較兩條路線之前，先確認兩邊是同一個量測定義。
一個漂亮的數字如果來自錯的定義，它會比沒有數字更危險 —— 沒有數字你會去量，
有錯的數字你會直接下結論。

---

## 3. 失敗（二）：他說「發燒友無法接受」，於是把聽感變成數字

2026-09-25 的投訴原話：「通過軟體後明顯變差」。

把當時的設定拿去量（96 kHz，Equalizer APO 內建 Benchmark 離線量測，不經喇叭）：

| 做法 | 立體相關（音場） | THD | 音量 |
|---|---|---|---|
| 只拆中側再還原 | 不變 | 0.001% | 0.00 dB（逐位元透明） |
| **當時在跑的**：兩側整條退 9 dB ＋ 真空管 ＋ Air | 0 → **+0.83**（幾乎變單聲道） | **0.730%** | **−10.9 dB** |
| 改成：只在 2.5 kHz 退兩側 −6、無飽和、補償 +1 | −0.085 → **−0.19**（音場留著） | **0.011%** | −4.0 dB |

**他是對的，而且數字比他的描述更難看。** 音場幾乎塌成單聲道、失真高了 66 倍、
整體小聲 10.9 dB（而小聲本身就會讓人覺得「變差」）。

修法：

1. **兩側退的是「女聲頻段」不是整條**（2.5 kHz 附近）→ 低頻與極高頻的立體感留著
2. **飽和外掛預設關掉** → THD 從 0.730% 降到 0.018%
3. 修好「整體音量補償」在沒勾 Air 時完全無效的缺陷
4. 「實測」按鈕多報一行音量差，提醒 **A/B 比較要等響度**

第 4 點是整個專案最反覆出現的陷阱：**比較兩個設定時，大聲的那個永遠贏。**

## 4. 失敗（三）：第 3 層原型走錯路線

2026-10-04。要做「即時神經網路人聲分離」。
先寫的原型用了離線級的模型（MelBand Roformer，913 MB）：

- 延遲 = 1.4 秒填窗 ＋ 推論 ＋ 0.1 秒 ≈ **1.5～2 秒**，門檻是 50 毫秒 → **差 30 倍**
- 這台沒有 CUDA（顯卡是 AMD），913 MB 的模型只能跑 CPU
- 每個窗開一條新 thread 而且自承沒鎖

**結構上做不到即時**，不是調參數的問題。

改用 **StemgenRT-5.8**（HS-TasNet 的分支，MIT 授權）：
hop 128、44.1 kHz、ONNX、官方標示 5.8 ms 演算法延遲、一條 CPU thread、權重有 SHA-256 pin。

量到的：RTF 0.80（1 thread）、CPU 3.4%、延遲約 29 ms。可行。

**教訓**：「離線模型跑快一點」跟「即時模型」是兩種東西，不是同一種東西的兩個檔位。

## 5. 失敗（四）：動態 sidechain 做出來了，量完**自己否決**

既然神經網路的瑕疵不該進訊號路徑，那就讓它只當**偵測器**：
用它判斷「女聲在不在」，去動態驅動一個完全透明的 mid/side EQ。
瑕疵永遠不進喇叭。這個想法很漂亮。

**偵測器本身是有效的**：女聲段的人聲／伴奏帶內比 10.73 dB，間奏段 2.85 dB，差了 7.9 dB。

**但交易是虧的**：

| | 靜態 | 動態 | 差 |
|---|---|---|---|
| 女聲前移（人聲／伴奏） | **2.41 dB** | 1.91 dB | −0.5 |
| 女聲前移（中央／兩側） | **4.02 dB** | 2.70 dB | −1.3 |
| 間奏的音場保留（越接近 0 越好） | −3.81 dB | **−3.50 dB** | +0.31 |

拿 0.5～1.3 dB 的女聲前移，換 0.31 dB 的音場。**不值得。**

**結構性原因（調參數救不回來）**：商業流行樂的人聲密度太高。
那 40 秒裡有 45% 的 hop 有人在唱，而「沒唱」的空隙是**字與字之間的零點幾秒**，不是長間奏。
「間奏時把音場還回來」—— 沒有東西可以還。

**教訓**：做完要量，量完要敢推翻自己。這個功能從想法到否決花了一天，
但如果不量，它會以「聽起來好像有差」的身分活在產品裡好幾年。

## 6. 失敗（五）：整晚卡住，因為裝完驅動沒重開機就改設定

即時版需要一條虛擬音訊線（VB-Cable）。它的 readme 明寫「必須重開機」。

我沒重開，直接開始改端點格式、改 Internal SR、下 Disable/Enable。
線路從頭到尾**一個樣本都沒傳過去**。前後燒掉**三次重開機**追錯方向
（以為是 44100 vs 48000 的取樣率不合）。

**真正的解法**：乾淨移除 → 重開機 → 乾淨安裝（**完全不動任何設定**）→ 重開機 → **一次就通**
（RMS −15.1 dBFS、左右分離 58 dB）。原廠的 48 kHz 根本不需要動；
速率差異後來用 `auto_convert=True` 交給 Windows 轉就解決了。

**教訓**：在「還沒驗證過會不會動」的狀態上疊設定，等於把「裝壞了」跟「設定錯了」混在一起 ——
兩個都查不出來。驅動裝完先重開、先驗證基本功能，再碰參數。

**連帶踩到的**：`Disable-PnpDevice` 對 root 列舉的裝置會**排到下次開機才執行**。
我以為沒成功、繼續動別的，結果下次開機它真的被停用，端點整個消失。

## 7. 失敗（六）：測試程式本身壞掉，而我在懷疑受測物

驗證虛擬線通不通，寫了：先 `sd.rec(...)` 再 `sd.play(...)`。
錄回來永遠是 **−240 dBFS 全靜音** → 判定「線路不通」。

**根因**：`sd.play()` / `sd.rec()` / `sd.playrec()` **共用模組層的同一個全域串流槽**，
後呼叫的會把前一個停掉。所以我其實從來沒有同時放過音。

**正解**：同時收送一定要自己開**兩個獨立的** `sd.InputStream` 與 `sd.OutputStream`。

諷刺的是，線路後來證實**當時也真的不通**（第 6 節的原因）。
但在修好測試程式之前，**沒有辦法分辨是哪一個** —— 這才是真正的代價。

**教訓**：診斷卡住的時候，「測量裝置壞掉」要當成**第一順位假設**，不是想不出來才回頭想的最後一個。

## 8. 失敗（七）：裝置的區塊大小不可以沿用模型的 hop

即時版接上真實裝置後**會爆音**。虛擬線控制台顯示
`Pull loss 8,668 / Buffers 221,966`（3.9%），`Push loss 0` → 是**擷取端追不上**。

**根因**：我把 `blocksize = HOP = 128`（2.9 ms）直接設給 WASAPI 串流。
那是**模型**的 hop，不是音效卡扛得住的回呼週期。
引擎因此吃掉 1934 CPU 秒、開了 52 條執行緒（檔案模式量到的是 0.8 核）。

**而檔案模式的 30 分鐘耐久測試（62 萬 hop、只有 1 次 underrun）完全沒有暴露這個問題。**

**教訓**：「照時鐘餵 wav」≠「接上真實裝置」。驗收方法必須包含真實裝置的連續播放。

---

## 9. 失敗（八）：把 `DeviceState=4` 讀成「停用」，追了一整輪錯方向

M-DAC 在聆聽途中會從系統消失。查到端點 `DeviceState=4`，我讀成「停用」，
於是一路用 `Enable-PnpDevice`、`SetEndpointVisibility` 想把它啟用回來。

**`DeviceState` 是位元旗標：1=ACTIVE、2=DISABLED、4=NOTPRESENT、8=UNPLUGGED。**

4 是「裝置不在匯流排上」。那些 API 處理的是 2，對 4 **沒有東西可以啟用**。
`pnputil` 最後直接回我：`The device is not connected`。

**連帶的更正**：前一天端點消失時，我歸咎於「自己用 UI 自動化誤觸」—— **那也是錯的**，
真正的原因跟這次同一個。更正直接加在原始記錄上，不另開一條。

**教訓**：看到一個狀態碼，先查它的**正確語意**再行動。
查定義要三十秒，照著錯的語意行動要三小時。

---

## 10. 失敗（九）：漂移量成總量÷時間，得到 665 ppm 的假值

量兩端時脈漂移，用「總樣本數 ÷ 總時間」算，得到 **665 ppm**，看起來很嚴重。

**真值是 43 ppm。**

**根因**：串流啟動有一個固定偏移，除以 30 秒的量測長度之後，
那個固定偏移被**放大成假的漂移**。

**正解**：漂移是**斜率**，要用線性回歸求，而且要丟掉前 20% 的暖機段。

---

## 11. 真因：要求 USB DAC 用「非原生取樣率」會把它打下 USB

把上面那些都修掉之後，**還是爆音**。

用一支只做量測的程式（不放音樂、只送靜音）跑三分鐘，量兩端時脈：

- 擷取端（虛擬線）：**−12.4 ppm**，完美
- M-DAC：算出 **31,881 Hz**。那不是漂移，是**裝置中途掉出去了**

對照實驗：

| 輸出模式 | 結果 |
|---|---|
| WASAPI 獨佔 **44.1 kHz**（非原生） | 約 130 秒掉線，`DeviceState=4`，**只有關 DAC 電源再開才會回來** |
| WASAPI 獨佔 **96 kHz**（原生） | 180 秒不掉、零警告、時脈 −50 ppm |

觸發條件是「切換取樣率讓韌體重鎖 PLL」，**不是獨佔模式本身**。

**這解釋了爆音**：輸出裝置會在聆聽途中掉線，不是演算法的問題。
之前修的三件事（blocksize、丟輸入、交叉淡化）都是真缺陷、也都修對了，但都不是主因。

**對日常聽音樂也有用的結論**：
**任何播放軟體都不要對 M-DAC 要求非 96 kHz 的獨佔輸出。**
「獨佔模式比較乾淨」不是免費的午餐。

## 12. 第 3 層的結局：做出來了、他說好聽、但不用

他的實聽結論是「好聽」。技術指標也都達成了：

- 延遲 29 ms（門檻 50 ms）
- 真峰 −1.00 dBFS
- 62 萬 hop 的耐久只有 1 次 underrun
- CPU 3.4%

**但硬體不配合，所以停用。** 他的話：「還是會爆音，不要用這一層了，其他留著試試。」

程式與量測工具全部留在 `sep_rt/`。要重啟這條線，先讀 PLAN.md 裡的
「已排除／還沒查」兩欄，**不要從頭再試一次**。

要讓它可用，剩下的工程是：引擎輸出改 96 kHz，所以需要 44.1→96 kHz 的串流重取樣
（模型固定 44.1 kHz）。建議用 `soxr` 的串流 API，不要自己刻多相濾波器。

Chrome 外掛那一層，估計 2～3 天。**一行都沒寫。**

原因：使用情境（在 Chrome 聽 YouTube Music）已經被第 1 層**完全覆蓋**了，

**這不是失敗，是投報率不對。** 值得寫下來，是因為它很容易被當成「還沒做完的事」。

## 14. 失敗（十）：花一天搜尋 300 組參數，結論是「原本那組就是對的」

第 1 層的 SIDE 曲線「2.5 kHz Q0.7 退 6 dB」當初是憑直覺選的。
拿去跟 **300 組候選**比（10 個頻率 × 5 個 Q × 6 個深度）。

**結果：沒有免費的午餐。**

| 設定 | 人聲對伴奏 | 音場代價 |
|---|---|---|
| 原聲 | +0.15 | 0 |
| **現行（2.5k Q0.7 −6）** | **+0.45** | **−3.82** |
| 2800 Q0.7 −12 | +0.82 | −4.09 |
| 2000 Q0.5 −12 | +1.88 | −5.46 |
| 1500 Q0.4 −12 | +2.84 | −7.21 |

Pareto 前緣**每一組都落在網格最深的 −12 dB** → 深度永遠有利，
是網格上限在擋，不是真的有甜蜜點。收益完全來自「退得更低頻、更寬、更深」，極限就是變單聲道。

在**相同的音場代價**下，最多只能從 +0.45 進到 +0.82 dB（大約在可聽閾值邊緣）。

**他盲聽了五個檔，選了現行那組。** 原本的直覺選擇就在他的甜蜜點上。

**這一天沒有白花**：它把「再調 EQ 參數」這條路**關掉了**，
逼我們去看訊號鏈上還沒被量過的那一段 —— 房間。

## 15. 真正的那一次：量房間

### 15.1 一句話的版本

訊號鏈每一段都調過、EQ 參數在 ±2 dB 裡反覆微調了好幾天。
然後量了房間 —— **63～200 Hz 隆起 +6 ~ +14 dB**。

> 我們拿放大鏡在修一面有裂縫的牆。

修掉之後，實聽評語從「好聽」變成「**超好聽**」。
那是整個專案最大的一次改善，而它花的時間比之前任何一次微調都短。

### 15.2 失敗（十一）：麥克風有 AGC，整條量測鏈是假的

第一次量出來的曲線亂七八糟，兩次量測對不起來。

決定性的證據：**播放更大聲，錄到的反而更小。**

```
amp=0.12 → RMS −45.6 dBFS
amp=0.18 → RMS −50.0 dBFS   ← 大聲 50%，錄到小 14 dB
```

這是 AGC（自動增益控制）還開著。

頻率響應量測的前提是**線性非時變**。有 AGC 的量測鏈兩個都不是。
所以這不是「量得不準」，是**完全沒有意義**。

修法：聲音控制台 → 錄製 → 麥克風 → 內容 → 增強功能 → 停用所有增強功能。
驗證方式：播兩個不同音量，看錄到的位準是不是**等比例**變化。

### 15.3 失敗（十二）：麥克風戴在頭上，誤差比訊號還大

量房間不能直接量。**要先證明這把尺是準的。**

做法：**EQ 開一次、關一次，兩次相減**。
差值應該精確等於 EQ 的設計曲線（那條曲線算得出來，因為參數是自己設的）。
麥克風的響應誤差、喇叭的響應、房間本身，在相減時**全部抵消** ——
這就是「不需要校正麥克風」的原因。

第一次的做法是：耳麥戴在頭上，人走過去按介面上的 A/B 鈕。

| | 平均絕對誤差 | 最大誤差 |
|---|---|---|
| 戴在頭上、人走過去按 EQ | **3.18 dB** | 7.67 dB |
| 固定在腳架、**切換由程式做** | **0.84 dB** | 2.08 dB |

**設計曲線的總起伏只有 3.43 dB。**
第一種做法的誤差跟訊號同量級 —— 這把尺量不出要量的東西。
那時候得到的任何「房間曲線」都是假的，照著它調只會害人去修一個不存在的問題。

在 350 Hz，波長約 1 公尺。**移動 10 公分就足以改變駐波圖樣。**

為了這件事，專門寫了 `tools/set_bypass.py`（用指令切 EQ 開關）
與 `tools/set_param.py`（改單一參數），讓**人不必進房間**。

### 15.4 分辨「這是房間」還是「這是麥克風」

未校正的麥克風有自己的響應，會混在曲線裡。有一個一次量測就能分離的辦法：

> **把麥克風移開 50 公分，再量一次。**
> 房間的駐波跟位置強烈相關 → 會變。
> 麥克風自己的響應跟位置無關 → 不會變。

實測：

- 低頻（≤315 Hz）移動後平均變化 **4.0 dB** → 房間
- 高頻（≥2.5 kHz）移動後平均變化 **1.2 dB** → 麥克風

所以曲線上 6.3 kHz 的 **+7.9 dB 是麥克風的臨場感提升，不是房間** —— 千萬不要去 EQ 它。

**沒做這一步就照著曲線修高頻，是這套流程最容易犯的錯。**

### 15.5 失敗（十三）：寬削把旁邊挖出一個洞

量到：63–200 Hz 隆起 +6~+14 dB，40–50 Hz 是深的凹陷。

第一個直覺是拿既有的 `warm`（150 Hz 低頻架式濾波器）寬削 −5 dB。

**峰是壓下去了，但 80–160 Hz 被挖出一個洞。**

正解是從實測**反推房間的原始曲線**，再解出最佳參數：

```
房間原始曲線 = 實測曲線 − 目前 EQ 的設計響應
最佳參數     = 讓「原始曲線 + 新 EQ」最接近平坦的那組
```

而且**一定要讓 Q 也進入搜尋**：

| 做法 | 50–250 Hz 的 RMS 偏差 |
|---|---|
| 寬的低頻架式濾波器削整段 | 5.09 dB |
| 窄濾波器但 Q 固定 1.0 | 3.81 dB |
| **讓 Q 自由（解出 Q=5.0）** | **2.36 dB** |

**原因**：那個 +13 dB 的峰在 63 Hz，而旁邊 50 Hz 是凹陷。
**Q 太寬，削峰的同時會把凹陷挖更深。**

放開 Q 之後有一個反直覺的結果：**低頻架式濾波器反而可以回到 +2.0 dB**。
用窄濾波器精準打掉峰之後，就不需要拿寬的工具去硬削整段低頻 ——
**低頻的厚度回來了，但轟隆的峰被壓住了。**

### 15.6 不要去填補凹陷

40 Hz −19 dB、50 Hz −11 dB 的凹陷，**不要碰**。

那裡的聲波在耳朵的位置互相抵消，推多少電力進去都抵消得掉。
只會讓喇叭在聽不到的頻率上做白工，甚至失真。

凹陷要靠**移動喇叭或座位**解決，不是 EQ。

### 15.7 結果

最終參數：**63 Hz Q5.0 −13 dB、125 Hz Q1.4 −10 dB、warm 回 +2.0 dB**（左右兩聲道等量）。

| | 修正前 | 修正後 |
|---|---|---|
| 63 Hz | +9.0 | **+0.1** |
| 80 Hz | +2.3 | +1.9 |
| 125 Hz | +6.3 | **+1.3** |
| 200 Hz | +2.1 | +3.7 |

63–200 Hz 全部收在 ±4 dB 內。

**他的評語：「超好聽」。**
這是三天以來第一次**量測、預測、實聽三者一致**。

### 15.8 撤回過的改動

曾經把五個模式的 `warm` 全部下移 6 dB（基於「要寬削」的假設）。
最佳化推翻那個假設之後，**全部改回原值**。

## 16. 最後的介面收斂

量完房間之後回頭看介面，有一半的控制項是**被自己的量測否決掉的功能**：

| 撤掉的 | 為什麼 |
|---|---|
| 真空管暖度 ＋ 推力 | 加 0.73% THD、立體相關拉到 +0.83（音場塌）。「發燒」模式本來就是為了關掉它而生的 |
| 通透：Airwindows Air | 要外掛 DLL、吃掉 4.6 dB 音量再自動補回來 |
| 伴奏退後量滑桿 | 跟最上面的「女聲控制」是**同一個參數**的兩種刻度 |
| 淡／中／濃 三個模式 | 彼此只差幾 dB，實際只在發燒／深夜／鋼琴之間切 |

剩下五顆鈕：**切回原聲 ／ 深夜甜嗓 ／ 鋼琴（發燒）／ 發燒甜嗓 ／ 重設旋鈕**，
加上一盞**房間修正燈**（告訴你量出來的修正正在作用，以及削了多少）。

順手修掉兩個 bug：

**一、「重設旋鈕」原本會把量出來的房間修正也一起歸零。**
房間修正是**房間**的屬性，不是聆聽模式的屬性 —— 模式鈕有遵守這條規則，重設沒有。

**二、撤掉真空管的勾選項之後，沒裝 VST 外掛的人被鎖死了。**
參數還在（`深夜甜嗓` 仍然會打開真空管），但畫面上已經沒有地方可以取消勾選 ——
於是會寫出一行指向不存在的 DLL 給 Equalizer APO。
修法：找不到檔案時整段跳過。**撤掉一個控制項，要先想清楚它控制的東西是不是也跟著消失了。**

### 說明做進介面

量完房間、收斂完介面之後，剩下一個問題：**這些「為什麼」寫在哪裡？**

寫在 README 裡，複製程式的人不會帶走；寫成外部檔案，檔案會跟程式走散。
所以直接做成介面上的頁籤 —— **調整台 ／ 方法論 ／ 調整過程 ／ 模式差別**，
全文以常數嵌在 `vocal_focus_gui.py` 裡面。複製到哪台機器，理由都跟著走。

其中「模式差別」那一頁的參數對照表是**程式開頁時從 `PRESETS` 即時產生**的，
不是寫死的文字。寫死的話，以後有人改了預設值，說明頁就會悄悄變成假的 ——
而「說明跟程式對不上」這件事，正是這份紀錄從頭到尾在對抗的東西。

## 17. 回頭看：什麼有用，什麼沒用

**真正有用的，兩樣：**

1. **mid/side 女聲前移**（第 1 層）—— 做好之後一直在跑，而且盲聽證實原本的直覺參數就是對的
2. **房間修正** —— 最大的一次改善，而且花的時間最短

**做出來但不用的：**

- 即時神經網路分離（第 3 層）：技術指標全達成、他說好聽，但 M-DAC 會從 USB 掉線
- 動態 sidechain：量完自己否決，交易是虧的
- 真空管、Air：被自己的量測否決

**從未開工而且應該如此的：**

- Chrome 外掛（第 2 層）：使用情境已被第 1 層覆蓋

**最貴的教訓，三條：**

1. **先量你還沒量過的那一段。** 我們在 ±2 dB 的範圍裡微調了好幾天，
   而訊號鏈末端躺著一個 **+14 dB** 的問題，只因為它在「量測邊界」之外。
2. **先證明尺是準的，再拿它量東西。** 兩次失敗（AGC、麥克風會動）都是尺的問題，
   不是受測物的問題。而兩次都一開始被當成受測物的問題。
3. **敢推翻自己的數字。** 第 2 節那個 +7.42 dB 的漂亮數字，差一點就讓整條神經網路路線
   在還沒開始之前就被誤殺。
